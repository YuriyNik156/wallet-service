# Design Document — Wallet Service

## 1. Назначение проекта

Разработать небольшое REST API-приложение для управления балансом пользовательских кошельков.

Приложение должно предоставлять два основных API-операции:

* изменение баланса кошелька;
* получение текущего баланса кошелька.

Особое внимание должно быть уделено корректной работе при конкурентных запросах на изменение одного и того же кошелька.

Проект является тестовым заданием для Python Backend Developer.

Основной принцип разработки:

> **KISS — реализовать только необходимую функциональность без преждевременного усложнения архитектуры.**

Не добавлять функциональность, отсутствующую в исходном ТЗ, если она не требуется для корректной работы или тестирования приложения.

# 2. Исходные требования

### Endpoint

```http
POST /api/v1/wallets/{WALLET_UUID}/operation
```

### Request

```json
{
  "operation_type": "DEPOSIT",
  "amount": 1000
}
```

Допустимые операции:

### Endpoint

GET /api/v1/wallets/{WALLET_UUID}

# 4. Архитектура приложения

Общая схема:

```text
Client
  ↓
FastAPI (маршруты и функция операции в app/wallets.py)
  ↓
SQLAlchemy Async (AsyncSession)
  ↓
PostgreSQL
```

Отдельного слоя сервисов или репозиториев нет. Маршруты и функция выполнения операции над кошельком находятся в `app/wallets.py`; работа с БД выполняется через SQLAlchemy и асинхронную сессию, передаваемую в функцию.

Docker-инфраструктура:

```text
Docker Compose
├── app
│   └── FastAPI application
│
└── db
    └── PostgreSQL
```

## 4.1. Ответственность компонентов

### FastAPI (`app/wallets.py`, `app/main.py`)

Отвечает за:

* HTTP endpoints;
* получение параметров запроса;
* валидацию входных данных через Pydantic;
* формирование HTTP-ответов;
* обработку HTTP-ошибок.

### Функция операции (`app/wallets.py`)

Бизнес-логика операций с кошельком в одной функции, принимающей `AsyncSession`:

* `DEPOSIT`;
* `WITHDRAW`;
* проверка достаточности средств;
* изменение баланса;
* управление транзакцией;
* обеспечение корректного конкурентного доступа.

### SQLAlchemy

Отвечает за взаимодействие Python-приложения с PostgreSQL.

Используется асинхронный API SQLAlchemy.

### PostgreSQL

Отвечает за:

* хранение данных;
* транзакционность;
* блокировки строк;
* атомарное изменение баланса;
* дополнительную защиту целостности (`CHECK`).

# 5. Модель данных

Для MVP используется одна таблица.

## 5.1. `wallets`

| Поле         | Тип БД                     | Тип в SQLAlchemy                | Назначение             |
| ------------ | -------------------------- | ------------------------------- | ---------------------- |
| `id`         | UUID                       | `uuid.UUID`                     | Первичный ключ         |
| `balance`    | `NUMERIC(20, 0)`, NOT NULL | `Decimal`                       | Текущий баланс         |
| `created_at` | `TIMESTAMPTZ`, NOT NULL    | `DateTime(timezone=True)`       | Дата и время создания  |
| `updated_at` | `TIMESTAMPTZ`, NOT NULL    | `DateTime(timezone=True)`       | Дата и время изменения |

### Ограничения

`id`:

* уникальный;
* primary key;
* UUID.

`balance`:

* точное числовое значение, PostgreSQL `NUMERIC(20, 0)` (целые рубли);
* `NOT NULL`, начальное значение — `0` (`server_default`);
* `CHECK (balance >= 0)` — ограничение объявляется и в модели (`CheckConstraint`), и в начальной миграции.

Основной проверкой достаточности средств остаётся бизнес-логика операции; `CHECK` — дополнительная защита от отрицательного баланса на уровне БД.

`created_at`, `updated_at`:

* временные метки с часовым поясом (`DateTime(timezone=True)`);
* `created_at` задаётся БД: `server_default=func.now()`;
* `updated_at` имеет `server_default=func.now()` и явно обновляется при каждом успешном изменении баланса.

## 5.2. Согласование типов суммы и баланса

| Уровень                     | Тип                                                  |
| --------------------------- | ---------------------------------------------------- |
| Входной `amount` (JSON)     | целое число                                          |
| Pydantic-схема запроса      | `StrictInt`, `gt=0`, `le=MAX_AMOUNT`                 |
| SQLAlchemy-модель           | `Decimal` (`Numeric(20, 0)`)                         |
| Колонка PostgreSQL          | `NUMERIC(20, 0)`                                     |
| Pydantic-схема ответа       | `balance: int`                                       |
| Ответ JSON                  | число (не строка)                                    |

Правила:

* `StrictInt` отклоняет строки (`"1000"`), дробные значения и `bool`;
* `MAX_AMOUNT = 10**12` — единая константа, используется в валидации API и в тестах. Она существенно меньше предела колонки (`10**20 - 1`), поэтому переполнение `NUMERIC` недостижимо на практике, а слишком большая сумма даёт 422, а не 500;
* арифметика над балансом выполняется в `Decimal`; `Decimal` с нулевой дробной частью преобразуется в `int` без потери точности;
* без дробных сумм, копеек и нескольких валют;
* Pydantic v2 сериализует `Decimal` в JSON строкой, поэтому схема ответа должна объявлять `balance: int`; тесты обязаны проверять числовой тип `balance` в JSON, а не только значение.

# 6. Бизнес-правила

## 6.1. Сумма операции

`amount` должна быть строго положительным целым числом, не превышающим `MAX_AMOUNT`:

```text
0 < amount <= MAX_AMOUNT
```

Значения `amount = 0`, `amount < 0`, `amount > MAX_AMOUNT`, нецелые и нечисловые значения не допускаются (HTTP 422).

API принимает сумму как целое значение рублей. Использование `float` не требуется.

Для хранения баланса используется PostgreSQL `NUMERIC(20, 0)`, чтобы избежать проблем с неточностью floating-point арифметики.

---

## 6.2. DEPOSIT

При операции:

```text
DEPOSIT
```

баланс увеличивается:

```text
new_balance = current_balance + amount
```

---

## 6.3. WITHDRAW

При операции:

```text
WITHDRAW
```

перед списанием необходимо проверить наличие достаточного баланса:

```text
amount <= current_balance
```

Если средств недостаточно:

* операция не выполняется;
* баланс не изменяется;
* транзакция откатывается;
* API возвращает HTTP 409 с телом `{"detail": "Insufficient funds"}`.

Списание суммы, точно равной балансу, допустимо (остаток `0`).

Баланс никогда не должен становиться отрицательным.

---

# 7. Конкурентность

Конкурентная обработка является одним из ключевых требований задания.

Несколько HTTP-запросов могут одновременно работать с одним кошельком.

Например:

```text
Initial balance = 1000

Request A:
WITHDRAW 700

Request B:
WITHDRAW 700
```

Ожидаемый результат: **ровно одна операция успешна** (HTTP 200), **вторая отклоняется из-за недостатка средств** (HTTP 409). Итоговый баланс — `300`.

## 7.1. Проблема race condition

Нельзя реализовывать изменение баланса как последовательность независимых операций:

```text
read balance
↓
check balance
↓
calculate new balance
↓
save balance
```

Без блокировки два конкурентных запроса могут прочитать одно и то же старое значение баланса (в примере выше обе операции прошли бы, и баланс оказался бы неверным).

---

## 7.2. Транзакция

Изменение баланса выполняется внутри одной явной транзакции (`async with session.begin()`). Проверка достаточности средств и изменение баланса находятся в этой же транзакции.

```text
BEGIN
  ↓
SELECT wallet FOR UPDATE
  ↓
check operation
  ↓
change balance (+ updated_at)
  ↓
COMMIT
```

При ошибке (кошелёк не найден или недостаточно средств):

```text
BEGIN
  ↓
SELECT wallet FOR UPDATE
  ↓
business error
  ↓
ROLLBACK
```

Исключение, вызванное бизнес-ошибкой, выбрасывается внутри блока транзакции и приводит к откату; оно не перехватывается внутри этого блока.

---

## 7.3. Row-level locking

Для получения кошелька при изменении баланса используется блокировка строки PostgreSQL:

```sql
SELECT ...
FROM wallets
WHERE id = ...
FOR UPDATE;
```

Блокирующий запрос выполняется **до** чтения баланса для бизнес-проверки; блокировка удерживается до завершения транзакции. Перед ним в той же сессии кошелёк не читается (иначе можно получить устаревший объект из identity map).

Если второй запрос пытается изменить тот же кошелёк одновременно:

```text
Request A
    ↓
SELECT ... FOR UPDATE
    ↓
🔒 wallet locked
    ↓
change balance
    ↓
COMMIT
    ↓
🔓 unlock

Request B
    ↓
SELECT ... FOR UPDATE
    ↓
⏳ waiting
    ↓
receives updated wallet
    ↓
checks current balance
```

Таким образом, операции над одним кошельком выполняются корректно даже при конкурентных HTTP-запросах. Разные кошельки блокируются независимо. Блокируется ровно одна строка за транзакцию, поэтому взаимоблокировки невозможны.

Уровень изоляции — стандартный `READ COMMITTED`, не меняется: после ожидания блокировки `FOR UPDATE` перечитывает актуальную версию строки. Более строгие уровни изоляции не используются (они привели бы к ошибкам сериализации).

Ограничение: блокировка держится всю транзакцию, и запросы к одному «горячему» кошельку занимают соединения из пула SQLAlchemy. Для масштаба задания это приемлемо.

Если кошелёк не найден, `SELECT ... FOR UPDATE` не возвращает строк — HTTP 404.

---

# 8. Асинхронная обработка

FastAPI и SQLAlchemy используются в асинхронном режиме.

Асинхронность позволяет приложению эффективно обрабатывать множество HTTP-запросов, пока отдельные операции ожидают I/O, например ответ PostgreSQL.

При этом асинхронность не отменяет необходимость транзакций и блокировок.

Используются две разные концепции:

```text
Async FastAPI
→ эффективная обработка множества запросов

Transaction + Row-level Lock
→ корректность конкурентного изменения одного кошелька
```

## 8.1. Сессии

* для каждого HTTP-запроса создаётся отдельная `AsyncSession`, предоставляемая через `Depends`;
* одна сессия никогда не используется несколькими конкурентными задачами (в том числе в тестах);
* `async_sessionmaker` создаётся с `expire_on_commit=False`, иначе чтение атрибутов после `commit()` в async-режиме приводит к ошибке lazy-load (`MissingGreenlet`);
* строка подключения читается из переменной окружения `DATABASE_URL` (драйвер `postgresql+asyncpg://`).

# 9. API

Контракт ответов одинаков для обоих эндпоинтов.

| Ситуация                                  | HTTP | Тело                                       |
| ----------------------------------------- | ---- | ------------------------------------------ |
| Успех (`GET` и `POST`)                    | 200  | `{"wallet_id": "<uuid>", "balance": 1500}` |
| Кошелёк не найден (`GET` и `POST`)        | 404  | `{"detail": "Wallet not found"}`           |
| Недостаточно средств (`POST`, `WITHDRAW`) | 409  | `{"detail": "Insufficient funds"}`         |
| Ошибка валидации запроса                  | 422  | стандартный формат FastAPI                 |

`balance` — число JSON (целое), а не строка.

Валидация запроса выполняется до обращения к БД, поэтому запрос с некорректным телом к несуществующему кошельку возвращает 422, а не 404.

## 9.1. Получение баланса

```http
GET /api/v1/wallets/{wallet_uuid}
```

* кошелёк существует — HTTP 200, `{"wallet_id": "<uuid>", "balance": <int>}`;
* не найден — HTTP 404, `{"detail": "Wallet not found"}`;
* некорректный UUID — HTTP 422.

---

## 9.2. Изменение баланса

```http
POST /api/v1/wallets/{wallet_uuid}/operation
```

Request:

```json
{
  "operation_type": "DEPOSIT",
  "amount": 1000
}
```

* успех — HTTP 200, актуальное состояние кошелька после операции: `{"wallet_id": "<uuid>", "balance": <int>}`;
* кошелёк не найден — HTTP 404, `{"detail": "Wallet not found"}`;
* `WITHDRAW` при `amount > balance` — HTTP 409, `{"detail": "Insufficient funds"}`;
* недопустимые значения — HTTP 422 (стандартный формат FastAPI):
  * неправильный UUID;
  * неизвестный `operation_type`;
  * `amount` не целое (строка, дробное, `bool`), `amount <= 0` или `amount > MAX_AMOUNT`;
  * отсутствие обязательных полей.

# 11. Миграции

Для управления схемой PostgreSQL используется Alembic с асинхронной конфигурацией (`alembic/env.py` на основе async-шаблона; URL берётся из `DATABASE_URL`, как и в приложении).

Начальная миграция создаёт таблицу `wallets` со всеми ограничениями из раздела 5: `NUMERIC(20, 0) NOT NULL DEFAULT 0`, `CHECK (balance >= 0)`, `TIMESTAMPTZ` с `server_default=now()`.

Миграции не заменяются автоматическим созданием таблиц ORM-моделями. Приложение не должно полагаться на `create_all` при запуске.

Миграции применяются командой контейнера приложения перед запуском Uvicorn (см. раздел 12). Применение миграций из lifespan приложения не используется.

# 12. Docker

Приложение и PostgreSQL запускаются в отдельных контейнерах.

```text
docker-compose.yml
│
├── app
│   └── Python + FastAPI
│
└── db
    └── PostgreSQL
```

Система должна запускаться одной командой на чистом клоне, без предварительного создания `.env`:

```bash
docker compose up --build
```

## 12.1. Конфигурация

* `docker-compose.yml` содержит безопасные для локальной разработки значения по умолчанию (например `${POSTGRES_PASSWORD:-postgres}`);
* `.env` необязателен и может использоваться для переопределения настроек; он не коммитится;
* `.env.example` документирует доступные переменные;
* реальные и производственные учётные данные в репозиторий не попадают;
* хост БД внутри Compose — `db`; приложение получает `DATABASE_URL` через переменные окружения.

## 12.2. Готовность PostgreSQL

Контейнер `db` имеет healthcheck с проверкой через TCP (официальный образ на этапе инициализации временно слушает только unix-сокет):

```text
pg_isready -h 127.0.0.1 -U $$POSTGRES_USER -d $$POSTGRES_DB
```

Двойной `$$` нужен, чтобы Compose не подставлял переменные сам, а передал их контейнеру. Контейнер `app` объявляет зависимость `depends_on: db: condition: service_healthy`.

## 12.3. Запуск приложения и миграции

Команда контейнера `app` выполняется последовательно:

```text
alembic upgrade head && python -m app.seed && uvicorn app.main:app --host 0.0.0.0 --port 8000
```

* Uvicorn запускается только после успешного применения миграций;
* если миграция завершается ошибкой, контейнер завершается с ошибкой, и приложение не стартует;
* seed выполняется после миграций (раздел 14);
* отдельный контейнер миграций не добавляется. Ограничение (для README): такая схема рассчитана на одну реплику приложения.

## 12.4. Порты

Порт PostgreSQL на хост не публикуется — для работы API это не требуется. Публикуется только порт приложения (`8000`). Если подключение к БД с хоста понадобится для отладки, это осознанное локальное решение, а не часть обязательного запуска.

Приложение не зависит от PostgreSQL, установленного на хостовой машине.

# 13. Тестирование

Используется `pytest` с `pytest-asyncio`; запросы выполняются через HTTPX (`AsyncClient` + `ASGITransport`).

Тесты запускаются в контейнере тем же образом: `docker compose run --rm app pytest` (команда заменяет стартовую команду, но БД поднимается и ожидается через healthcheck).

## 13.1. Тестовое окружение

* тесты используют отдельную БД `wallet_test` в том же контейнере PostgreSQL и не затрагивают данные разработки;
* `conftest.py` при необходимости создаёт БД `wallet_test` и применяет к ней миграции командой `alembic upgrade head` в синхронной фикстуре (до запуска async-тестов, не внутри работающего event loop). Таким образом, тесты работают на схеме из миграций, включая `CHECK`;
* строка подключения тестов задаётся до импорта приложения (через `DATABASE_URL`);
* кошельки создаются фикстурами с уникальным `uuid4`; данные других тестов не очищаются массовым `TRUNCATE`;
* конкурентные запросы получают собственные сессии: `get_session` не переопределяется общей сессией, а общий `AsyncSession` не передаётся в несколько задач;
* стратегия event loop и пула соединений выбирается с учётом версий pytest-asyncio и SQLAlchemy, чтобы исключить ошибки `attached to a different loop` и `Event loop is closed`. Предпочтительный вариант — один loop на всю тестовую сессию (`loop_scope="session"` в конфигурации pytest), запасной — `NullPool` для тестового engine. Окончательный выбор подтверждается при настройке тестов; сложная инфраструктура не добавляется.

## 13.2. GET

Проверить:

* получение существующего кошелька: HTTP 200, `wallet_id`, `balance` — число JSON (`int`), а не строка;
* несуществующий кошелёк: HTTP 404, `{"detail": "Wallet not found"}`.

## 13.3. DEPOSIT

Проверить:

```text
initial balance = 1000
DEPOSIT 500
result = 1500
```

* HTTP 200, `balance` — число JSON;
* последующий `GET` возвращает обновлённый баланс.

## 13.4. WITHDRAW

Проверить:

```text
initial balance = 1000
WITHDRAW 300
result = 700
```

Также:

```text
initial balance = 500
WITHDRAW 500
result = 0
```

(снятие суммы, равной балансу, успешно).

## 13.5. Недостаточно средств

Проверить:

```text
initial balance = 500
WITHDRAW 600

→ HTTP 409, {"detail": "Insufficient funds"}
→ balance remains 500 (проверяется через GET)
```

## 13.6. Несуществующий кошелёк при изменении

`POST` для несуществующего кошелька возвращает HTTP 404, `{"detail": "Wallet not found"}`.

## 13.7. Валидация

Проверить (HTTP 422, параметризованные тесты):

* `amount = 0`;
* отрицательный `amount`;
* `amount > MAX_AMOUNT`;
* строковый `amount` (`"1000"`);
* дробный `amount`;
* неизвестный `operation_type`;
* некорректный UUID;
* отсутствие обязательных полей.

## 13.8. Конкурентный сценарий

Отдельно проверить параллельные операции над одним кошельком.

```text
initial balance = 1000

10 concurrent requests
WITHDRAW 200
```

Ожидаемый результат:

* ровно 5 успешных ответов HTTP 200;
* ровно 5 ответов HTTP 409;
* ни одного ответа HTTP 500 и других неожиданных кодов;
* итоговый баланс равен `0` (проверяется через `GET`);
* баланс не становится отрицательным.

Каждый запрос выполняется отдельной задачей со своей сессией приложения (запросы реально идут в PostgreSQL на разных соединениях). Число параллельных запросов не должно превышать размер пула соединений.

Дополнительно: параллельные `DEPOSIT` и `WITHDRAW` по одному кошельку. Итоговый баланс должен быть равен начальному плюс сумма успешных пополнений минус сумма успешных списаний и не быть отрицательным.

## 13.9. Детерминированный тест блокировки

Конкурентный тест из 13.8 сам по себе не гарантирует, что запросы пересеклись во времени, поэтому его дополняет детерминированный тест, работающий с реальным PostgreSQL:

1. Отдельная сессия начинает транзакцию и блокирует строку кошелька `SELECT ... FOR UPDATE`.
2. Через API запускается операция над этим же кошельком (фоновая задача).
3. Проверяется, что запрос не завершился в течение короткого интервала (ожидает блокировку).
4. Первая транзакция завершается (`COMMIT`).
5. API-запрос завершается и возвращает ожидаемый результат, учитывающий актуальный баланс.

Тест использует отдельные сессии и соединения PostgreSQL; имитация конкурентности на уровне Python не засчитывается.

## 13.10. Проверка качества тестов

Один раз при разработке блокировка `FOR UPDATE` временно удаляется, и тесты 13.8 и 13.9 должны обнаружить нарушение. Это ручная проверка самих тестов; удаление блокировки не входит в штатный набор тестов и не остаётся в коде. Нагрузочные инструменты и многопроцессные сценарии не используются.

# 14. Seed / тестовые данные

Отдельный endpoint для создания кошелька не добавляется, поскольку его нет в исходном ТЗ.

Для автоматических тестов кошельки создаются через pytest fixtures.

Для ручной проверки используется `app/seed.py`:

* создаёт один кошелёк с заранее известным UUID (константа, документируется в README) и начальным балансом;
* идемпотентен: `INSERT ... ON CONFLICT DO NOTHING`; повторный запуск не создаёт дубликаты и не сбрасывает существующий баланс;
* выполняется после успешного применения миграций (раздел 12.3);
* не добавляет публичный endpoint и не создаёт других сущностей;
* позволяет проверить `GET` и `POST` сразу после `docker compose up --build`.

Seed не является частью публичного REST API и не превращается в систему наполнения данными.
